# Security checklist

How the app handles each OWASP Top 10 (2021) category, and what is still to do. ✅ = in place, 🔜 = planned for the named phase.

| Category                                           | How it's handled                                                                                                                                                                                                                                                                                                                                                                                                                                                                          | Status                                                                              |
| -------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| **A01 Broken access control**                      | One policy module (`src/server/policy/can.ts`) decides every permission. Resources are loaded first and checked against the signed-in user, and IDs from the URL or client are never trusted. Seller queries are scoped to the user's own seller profile. Suspended users are denied everything. The admin area returns 404 to non-staff. Unit tests cover cross-user reads and edits of listings, orders, conversations, payouts, reviews and disputes, and e2e tests cover role gating. | ✅                                                                                  |
| **A02 Cryptographic failures**                     | HTTPS everywhere with HSTS (2 years, preload). Sessions are handled by Clerk in HttpOnly, Secure, SameSite cookies. No card data is ever stored. Payout details are kept as provider references only. ID-document references are encrypted with AES-256-GCM; the documents sit in a private bucket and are only streamed to moderators through an authorised route.                                                                                                                       | ✅                                                                                  |
| **A03 Injection**                                  | Prisma parameterised queries only. The one raw query (Postgres search fallback) is built with `Prisma.sql` tagged templates, so every value is a bound parameter. Every server input is validated with Zod. React escapes all output. Rich text will go through an allow-list sanitiser if it is ever allowed.                                                                                                                                                                            | ✅                                                                                  |
| **A04 Insecure design**                            | Money is stored as integers. Order state machine with optimistic locking; idempotent payment webhooks keyed on the unique provider reference; stock reserved atomically; prices always recomputed on the server from the database, never taken from the client; amount and currency checked against the stored payment.                                                                                                                                                                   | ✅                                                                                  |
| **A05 Security misconfiguration**                  | Strict security headers: CSP, X-Frame-Options DENY, nosniff, Referrer-Policy, Permissions-Policy, COOP, HSTS, and no `x-powered-by`. Env validation refuses unsafe settings, such as dev sign-in when deployed. Dev tools 404 in production. See `docs/decisions.md` #3 for the CSP trade-off.                                                                                                                                                                                            | ✅                                                                                  |
| **A06 Vulnerable components**                      | `pnpm audit` in CI, and Dependabot weekly for npm and monthly for Actions. Exact versions are pinned for Next, Clerk and Prisma.                                                                                                                                                                                                                                                                                                                                                          | ✅                                                                                  |
| **A07 Identification and authentication failures** | Clerk handles passwords, OTP, Google sign-in, bot protection and session rotation. Rate limits cover sign-in, sign-up, OTP, password reset and role changes. 2FA is required for sellers with payouts and for staff.                                                                                                                                                                                                                                                                      | ✅ / 🔜 2FA enforcement (Phase 2 onboarding, Phase 5 staff)                         |
| **A08 Software and data integrity failures**       | The Clerk webhook signature is verified (Svix) before anything is trusted, and failures are written to the audit log. Paystack webhooks are verified with HMAC-SHA512 (constant-time compare) and each charge is re-checked with Paystack's verify API before money state changes. Lockfile installs use `--frozen-lockfile` in CI.                                                                                                                                                       | ✅                                                                                  |
| **A09 Logging and monitoring failures**            | Append-only `AuditLog` for role changes, admin actions and webhook signature failures. Sentry captures errors with personal data collection turned off (no cookies, headers, bodies or query strings).                                                                                                                                                                                                                                                                                    | ✅ / 🔜 alerts for spikes in failed logins, payments and webhook failures (Phase 5) |
| **A10 Server-side request forgery**                | The server makes no outbound requests based on user input. Image fetching in Phase 2 uses signed direct uploads to R2, never server-side fetches of user URLs.                                                                                                                                                                                                                                                                                                                            | ✅                                                                                  |

## Other requirements from the spec

- **Uploads (Phase 2, ✅):** signed direct-to-R2 uploads with the content type and exact size in the signature; type checked from the file's bytes; 10 MB, 300 px minimum and 40 MP maximum; re-encoded to WebP on the server (strips EXIF/GPS and anything hidden in the file); originals deleted; only `READY` images are public; raw uploads under `incoming/` are never served. Rate limited per seller. 🔜 ClamAV malware scan in the background worker (Phase 6).
- **Search (Phase 2, ✅):** filter values are quoted and escaped for Meilisearch; the Postgres fallback uses parameterised `Prisma.sql`. Search returns ids only and results are re-read from Postgres as `ACTIVE`, so the index can never leak drafts. Search is rate limited per IP.
- **Payments (Phase 3, ✅):** no card data touches our servers (Paystack hosted checkout). Seller M-Pesa numbers are sent to Paystack and only the recipient code and a masked label are stored. Checkout, order updates and payout settings are rate limited. Buyers and sellers can only see their own orders; the buyer's phone and address are shown to the seller only for paid orders. Cron routes require `CRON_SECRET`; dev payment and outbox pages 404 in production.
- **Trust and safety (Phase 4, ✅):** messages, reports, reviews, disputes and ID uploads are rate limited. Conversations, dispute photos and ID photos are checked against the viewer on every request (404 otherwise). Uploaded photos are type-checked from their bytes and re-encoded (EXIF/GPS removed). Moderators can't suspend other staff; every moderation action is in the audit log and the `ModerationAction` table. Contact details in messages before an order trigger a warning. 🔜 Turnstile on first messages (Phase 6).
- **Backups:** use the managed Postgres point-in-time recovery (Neon or Supabase), and document and drill a restore in Phase 6.
- **Data protection:** consent for analytics cookies, data export and account deletion. Deletion is a soft delete (`markUserDeleted`) that keeps financial records, followed by a hard delete after the retention period. Build in Phase 5.
- **Open redirects:** sign-in redirect targets are restricted to same-site relative paths.
